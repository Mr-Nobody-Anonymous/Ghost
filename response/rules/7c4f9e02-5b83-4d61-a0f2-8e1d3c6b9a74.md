# WMI Command-Line Event Consumer Created Under root\subscription

- Rule: `7c4f9e02-5b83-4d61-a0f2-8e1d3c6b9a74`
- Severity: medium
- ATT&CK: T1546.003
- Tactic: persistence
- Status: **drafted from the rule, not worked against a live alert**

## What fired

Sysmon event 20 - a permanent WMI consumer was registered. A CommandLineEventConsumer is the half that actually executes a command at trigger time, which is why it carries higher signal than the filter alone.

Event IDs in scope: 20.

## Triage

Check these in order. The first one that is empty means the rule matched on a field the collector did not populate.

- `EventID`
- `Computer`
- `Type`

Compare the registry/task/file artifact against a host at the same patch level. Persistence is not abnormal; unsigned persistence written from a user's session is.

## Containment

`disable-account` - Remove the persistence entry only after capturing its command line and the writing process. Then disable the account that created it: `net user <account> /active:no`.

Do not close out on the containment action alone. The entry being removed does not answer how it got there.

## What to preserve

- The alert's raw event, verbatim, before any field is normalised
- The host's clock offset from the collector
- The rule version that fired, from the rule's own id

## When this is a false positive

The behaviour this rule matches has legitimate causes on a managed host. Before closing, identify the parent process and whether the binary is signed; a signed path under `Program Files` with a service-account parent is the ordinary case.
