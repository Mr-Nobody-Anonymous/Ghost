# Beacon with Custom X-Id / X-Seq Headers

- Rule: `2d7f4b90-8e31-4c5a-b2d6-9f1a0c3e7d52`
- Severity: high
- ATT&CK: T1071.001
- Tactic: command-and-control
- Status: **drafted from the rule, not worked against a live alert**

## What fired

Detects outbound HTTP(S) requests carrying BOTH non-standard headers X-Id and X-Seq, or a request whose URI path is /poll with id= and seq= query terms under a browser-looking user agent. The original draft used `cs-uri-stem|endswith: '/poll'` with a conjunctive URI query, which never fired on the /poll?id=&seq= shape it was written for.

Event IDs in scope: none.

## Triage

Check these in order. The first one that is empty means the rule matched on a field the collector did not populate.

- `cs-header-X-Id`
- `cs-header-X-Seq`
- `SourceAddress`
- `DestinationHostname`
- `cs-uri-query`
- `cs-uri-stem`
- `cs-user-agent`

Compare the destination against the process that resolved it. A browser is expected to resolve unfamiliar names; an Office process is not.

## Containment

`block-domain` - Block the destination at the resolver and the proxy. Record the full URI and every header the proxy retained before the block goes in.

Do not close out on the containment action alone. The entry being removed does not answer how it got there.

## What to preserve

- The full URI, including query string
- Every proxy-retained header, particularly the custom ones
- The process that owned the socket, if the proxy export joins it

## When this is a false positive

Legitimate applications use HTTP for telemetry and updates. The custom-header pair is what separates this: a normal client does not send `X-Id` and `X-Seq` together with no cookie.
