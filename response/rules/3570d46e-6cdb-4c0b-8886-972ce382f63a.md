# Removable-Media Spreader Writes Executable and autorun.inf

- Rule: `3570d46e-6cdb-4c0b-8886-972ce382f63a`
- Severity: low
- ATT&CK: T1091, T1105
- Tactic: initial-access
- Status: **drafted from the rule, not worked against a live alert**

## What fired

A process creates an executable or `autorun.inf` on a drive letter that is not `C:`. This is the USB-spreading shape: the implant's spreader drops `svc_update.exe` and an `autorun.inf`, then relies on Windows' legacy AutoRun behaviour.
Windows 10 build 1703+ ignores AutoRun for non-optical removable media, so the `autorun.inf` half is largely historical; the executable-write half is what still matters. The underlying behaviour - a process writing an executable to a removable volume - has no dedicated Sysmon event, and this rule cannot tell a legitimate installer or backup tool from a spreader, which is why it is low level and paired with `autorun_inf_writes.yml`.

Event IDs in scope: 11.

## Triage

Check these in order. The first one that is empty means the rule matched on a field the collector did not populate.

- `EventID`
- `TargetFilename`

Check each field for presence before checking its value. A missing field means the collector never populated it, and a rule matching on nulls is quiet rather than empty.

## Containment

`quarantine-file` - Quarantine the delivering file and preserve its hash. The same file almost certainly reached other hosts.

Do not close out on the containment action alone. The entry being removed does not answer how it got there.

## What to preserve

- The alert's raw event, verbatim, before any field is normalised
- The host's clock offset from the collector
- The rule version that fired, from the rule's own id

## When this is a false positive

The behaviour this rule matches has legitimate causes on a managed host. Before closing, identify the parent process and whether the binary is signed; a signed path under `Program Files` with a service-account parent is the ordinary case.
