# Named Mutex Created by Unsigned Temp Process

- Rule: `1a2b3c4d-5e6f-4708-9a0b-1c2d3e4f5a0d`
- Severity: low
- ATT&CK: T1547.001
- Tactic: persistence
- Status: **drafted from the rule, not worked against a live alert**

## What fired

EDR-reported creation of a named mutex by a process launched from a user-writable path.

Event IDs in scope: none.

## Triage

Check these in order. The first one that is empty means the rule matched on a field the collector did not populate.

- `EventType`
- `Image`

Compare the registry/task/file artifact against a host at the same patch level. Persistence is not abnormal; unsigned persistence written from a user's session is.

## Containment

`disable-account` - Remove the persistence entry only after capturing its command line and the writing process. Then disable the account that created it: `net user <account> /active:no`.

Do not close out on the containment action alone. The entry being removed does not answer how it got there.

## What to preserve

- The registry key's full path and its last-write time
- The `Details` value verbatim, including quoting
- The `Image` process that wrote it, and its parent
- A copy of the value before any cleanup

## When this is a false positive

An approved installer writing a Run key, and the software update mechanism refreshing it afterwards. Both are legitimate and both look identical at the registry level - the discriminator is the writing process's signature and path, not the key.
